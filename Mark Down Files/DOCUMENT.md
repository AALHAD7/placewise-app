## PHASE 1: PLANNING & ARCHITECTURE

### Step 1 — Project Ideation & Validation ✅
- Identified problem: B-school students use 5+ scattered tools for interview prep
- Defined solution: AI-powered RAG-based platform with community verification
- Defined target users: IIM Tiruchirappalli 2nd year (250 students) → Phase 2: UG engineering
- Defined key differentiators: RAG (no hallucinations), community-verified, integrated workflow, company-specific, affordable

### Step 2 — Architecture Design ✅
- Chose tech stack: React + Tailwind (frontend), Node.js + Express (backend), Supabase PostgreSQL + pgvector (database)
- Chose deployments: Vercel (frontend), Render.com (backend)
- Designed RAG pipeline: User query → pgvector similarity search → top 5 chunks → Claude with grounded context → confidence score

### Step 14a — Real Resume File Upload + Parsing (2026-08-13)
User wanted the actual file picker to work end-to-end (upload → real text extraction → real Gemini generation), not just the paste-text fallback. Added:
- **New deps**: `multer` (multipart/form-data handling), `pdf-parse` v2 (PDF text extraction, note the v2 API is `new PDFParse({data: buffer}).getText()`, not the old v1 `pdf(buffer)` function form), `mammoth` (`.docx` text extraction).
- **`POST /api/resume/upload`** (auth required, `backend/src/routes/resume.js`) — accepts multipart field `resume`, extracts text by extension (`.txt` direct, `.pdf` via pdf-parse, `.docx` via mammoth; legacy `.doc` explicitly rejected — no good pure-JS parser for the old binary format), returns `{resumeText, fileName, truncated}`.
- **Design file**: `resume.onFile` now calls a new `uploadResumeFile()` class method — uploads the real file, populates the (already-built) resume textarea with the extracted text, then automatically calls the same `runResumeGenerate()` used by the manual paste flow. The "Google Drive" button stays a fake stub — real Drive OAuth/API integration is out of scope.
- Verified all 3 file types (`.txt`, a real 322KB PDF from `Data/`, a `.docx` from mammoth's own test fixtures) extract correctly.

Two real bugs found and fixed while testing this:
1. **Multer errors bypassed JSON responses.** Tested with an unrealistically huge 80MB PDF (a full casebook, not a resume) to check the 10MB limit — Multer's rejection happened in middleware before the route's own try/catch could run, so it fell through to Express's default HTML error page instead of JSON. Fixed with a global JSON error-handling middleware in `server.js` (also converts any other uncaught route error to JSON, not just this one).
2. **No cap on resume text length caused a near-hang.** Fed a legitimately-parsed but unrealistic 53KB/33-page PDF (an interview-experience casebook, not an actual personal resume) through to `/api/resume/interrogate` and the embedding call took long enough to look hung. Added `MAX_RESUME_CHARS = 6000` (generous for an actual 1-2 page resume) truncation in both `/upload` and `/interrogate`, so a mis-upload can't send an oversized embedding request. Re-tested with the same file post-fix — completes in bounded time (~27s, not indefinite).

### Step 14d — Live Captions While Recording (2026-08-14)
User asked whether spoken words could appear in the text box live, as they talk, rather than only after clicking Stop. Real constraint surfaced and explained to the user before building: Gemini's `generateContent` API has no real-time streaming mode — chunking audio to it every few seconds would look laggy/bursty, not smooth. Presented the tradeoff and user chose: browser-native live preview (Web Speech API) while recording, replaced by the existing accurate Gemini transcript once recording stops.

Implementation in `Web Design/Placement Mastery Hub.dc.html`:
- `startRecording(k)` now also starts a `SpeechRecognition`/`webkitSpeechRecognition` instance (`continuous: true`, `interimResults: true`, `lang: "en-IN"`) alongside the existing `MediaRecorder`. Its `onresult` writes live interim text straight into the answer field as the user talks.
- Text existing in the answer field *before* recording started (`baseText`, captured at the top of `startRecording`) is preserved and prepended — live preview appends after it rather than wiping out anything already typed.
- On stop, the live-preview text is **replaced** (not appended to) by Gemini's final transcript from `/api/transcribe` — both cover the same recorded segment, so appending would duplicate it. `baseText` is reused as the prefix for this replacement too.
- Best-effort only: if `SpeechRecognition` isn't available (e.g. Firefox), recording still works exactly as before, just without the live preview — `recognizer.onerror` is a silent no-op since Gemini's transcript on stop remains the actual source of truth regardless of whether the live preview worked.
- New instance field `_recognizers` (alongside the existing `_recorders`) holds the live recognizer per question-id, same non-serializable-state reasoning.
- Fixed a real bug caught before testing: `startRecording`'s `baseText` line read `this.state.answers[k]` unguarded — `answers` can be `undefined` before any answer exists, which would throw. Fixed to `(this.state.answers || {})[k]`.

### Step 14f — Real Generation Progress on the Generate Button (2026-08-14)
User wanted transparency during question generation: "how much generation of the questions has happened, like, twenty percent, thirty percent" — not just a static "Generating…" label. Gemini's `generateContent` has no notion of progress on its own, but its streaming variant (`streamGenerateContent`, SSE) delivers the same output incrementally as it's produced, which gives real (not simulated/timer-based) progress.

Backend (`backend/src/lib/gemini.js`, `backend/src/routes/resume.js`):
- Added `streamGenerateJSON()` — calls `:streamGenerateContent?alt=sse`, accumulates the streamed text, and invokes an `onProgress(rawSoFar)` callback after every chunk.
- `POST /api/resume/interrogate` now responds as `text/event-stream` instead of one JSON blob. It estimates progress by counting occurrences of `"level":` in the partial output (every question object emits exactly one, and the target is always 30 questions), sends `{type:"progress", percent}` events as that count climbs, then `{type:"done", results, sourcesUsed}` once the full response parses as valid JSON, or `{type:"error", ...}` on failure.

Frontend (`Web Design/Placement Mastery Hub.dc.html`):
- `runResumeGenerate()` rewritten to read the response body as a stream (`res.body.getReader()`) instead of `res.json()`, parsing SSE events and updating `resumeGenPercent` in state as progress events arrive.
- Generate button label now reads `"Generating… NN%"`, and a small progress bar (same visual pattern as the upload progress bar) appears underneath it while generating.

Bug caught during testing, not obvious from any docs: Gemini's SSE stream separates events with `\r\n\r\n`, not the plain `\n\n` assumed from a first pass at the SSE spec. Splitting on `\n\n` never matched, so the entire streamed response sat in the buffer and was silently discarded when the stream closed — every request failed with "No JSON found in model output" despite the model succeeding. Fixed by splitting on `/\r?\n\r?\n/` in both the backend (`streamGenerateJSON`) and the frontend (`runResumeGenerate`), and by flushing any leftover buffered text after the read loop ends (the final event isn't always followed by a trailing separator). Verified end-to-end after the fix: 30-question generation streamed ~26 real progress ticks (5% → 99%) over ~10s and returned all 3 categories correctly.

### Step 14g — Real, Blunt Per-Answer Feedback (2026-08-14)
User caught that "Get feedback" was fully hardcoded — three canned `{good, fix}` objects cycled by array index (`FEEDBACK[i % FEEDBACK.length]`), completely unrelated to the question or the answer actually typed/spoken. Explicit instruction: feedback must be generated from the real question + real answer, and must be **blunt, not sugar-coated** — the user's reasoning: a softened critique here teaches the candidate to give the same soft answer in a real interview, where it will land badly.

Backend (`backend/src/routes/resume.js`):
- New `POST /api/resume/feedback` — takes `{question, answer}`, calls Gemini once (`generateJSON`, non-streaming — this response is short, no need for progress) with a system prompt that explicitly forbids unearned positives, requires every point to reference something concrete from that exact answer, and allows the "good" array to be sparse or empty if the answer genuinely has nothing working in its favor. Returns `{success, good: [...], fix: [...]}`.

Frontend (`Web Design/Placement Mastery Hub.dc.html`):
- Removed the hardcoded `FEEDBACK` array from `withAnswers()` entirely.
- Added `runFeedback(k, question, answer)`, called from each question's `getFeedback` handler; tracks per-question state as `{loading}` → `{good, fix}` or `{error}`.
- "Get feedback" button now reads "Thinking…" and disables while the request is in flight; a line of copy ("Reading your answer and thinking it through — this is blunt, not scripted, so it takes a moment…") shows during that wait so the delay reads as intentional, not broken.

Verified with a deliberately weak, rambling test answer — Gemini's response was concretely critical (called out vague phrasing, missing structure, casual language) rather than generic, confirming the tone matches what was asked for.

### Step 14h — Self-Improving Feedback Loop (2026-08-14)
User wanted the feedback feature to "learn on itself": as more people use it (their framing — 1,000 users, ~200 giving similar-situation answers), quality should improve by leaning on that accumulated data, rather than treating each answer in isolation forever.

Clarified with the user before building: literally training/fine-tuning a custom LLM isn't practical here (no training infra, and nowhere near enough data even at 1,000 users) — but a retrieval-based version achieves the same practical outcome using infrastructure already in this codebase (the same pgvector similarity-search pattern used for resume question generation). User confirmed this approach and chose to store examples **anonymized** (no `user_id`) rather than linked to individual users.

Backend:
- New table `answer_feedback_examples` (`backend/db/migration_004_answer_feedback_examples.sql`): question, `question_embedding` (vector(768)), answer, `good`/`fix` (jsonb arrays). No user identity stored.
- New RPC `match_answer_feedback_examples(query_embedding, match_count)` — same shape as the existing `match_document_chunks`.
- `POST /api/resume/feedback` (`backend/src/routes/resume.js`) now: embeds the incoming question → retrieves the 3 most similar past question/answer/feedback examples → includes them in the Gemini prompt as calibration context ("here's how similar situations were judged before — judge this the same way, don't copy wording") → generates feedback as before → **after** responding to the user, stores the new question/answer/feedback as a fresh example (fire-and-forget, doesn't block or risk the user's response if the insert fails).

Two real bugs hit and fixed while verifying this, neither obvious from Supabase's docs:
1. **RLS silently blocking inserts.** The user had enabled Row-Level Security on this table (a reasonable instinct in general) while it had zero policies, so every insert failed with `42501`. Explained why RLS doesn't apply here: nothing talks to Supabase directly except this backend, which uses the `service_role` key and already gates access via `requireAuth` — matching every other table in this schema (`document_chunks`, `news_cache`, etc.), none of which have RLS on. Fixed with `alter table answer_feedback_examples disable row level security;`.
2. **A near-empty ivfflat index silently returning zero matches.** The migration originally created an `ivfflat` index (`lists = 100`) immediately, copying the `document_chunks` pattern. But `document_chunks` is bulk-loaded with thousands of rows *before* its index is built, while this table starts at zero rows and grows one at a time from live traffic. With only 1-2 rows, ivfflat's clustering is degenerate and the default probe count came back with **zero** results even though an exact match plainly existed in the table — confirmed by testing the RPC directly via raw REST calls, isolating it from any client-library or RLS issue. Fixed by dropping the index entirely (`drop index if exists answer_feedback_examples_embedding_idx;`) — a plain sequential scan via pgvector's `<=>` operator is fine up to tens of thousands of rows, which this table won't approach soon. **Left as a commented-out statement in the migration file, to add back once there's real volume of stored examples** — same caveat as `document_chunks`' own index, just discovered the hard way here.

Verified end-to-end after both fixes: stored one example, then submitted a semantically similar (but numerically different) answer to a different phrasing of the same underlying question — `match_answer_feedback_examples` correctly ranked the true match at 0.875 similarity vs. 0.665 for an unrelated stored example, and the new feedback's "fix" points echoed the same critique pattern as the retrieved example (calling out missing conflict/trade-off detail in both), confirming the retrieved context is actually shaping generation, not just sitting unused in the prompt.

### Step 14v — Generation Model Swap + Cascade (2026-09-01) ✅
User asked why the app wasn't using Gemini 3.5 Flash-Lite (released July 2026, after this session's own knowledge cutoff — confirmed it's real and live against the actual API key before touching anything). **Architecture decision, made and explained up front**: code execution runs entirely client-side via WASM (`sql.js` for SQL, Pyodide for Python) rather than any server-side execution API - free, real-time (no network round-trip per run), and avoids introducing a paid/rate-limited third-party dependency, consistent with this project staying on free-tier infra throughout. Given the CPU-load incident from the reverted local-embedding attempt (Step 21b), explicitly sanity-checked both runtimes' actual footprint before committing to the design rather than assuming: `sql.js` loads in ~4ms, Pyodide in Node loads in ~800ms - both lightweight (unlike the earlier embedding model, these aren't doing heavy ML inference, just interpreting/executing small scripts), so no repeat of that problem.

**The core design principle for grading**: never trust Gemini's own claim of what a query/function *should* return - a hand-typed "expected result" is exactly the kind of thing a model can get subtly wrong. Instead, the generated reference solution is actually **executed** (server-side, via the same `sql.js`/Pyodide runtimes used client-side) to compute the real expected result, which is what a user's submission gets checked against. Live-tested both pipelines end-to-end with real Gemini output before writing any frontend code: a cold SQL generation produced a genuinely non-trivial CTE + window-function problem (delivery-partner ranking) that executed cleanly on the first attempt; a cold Python generation produced a correct dict-aggregation problem, likewise clean on the first attempt.

- **`backend/db/migration_010_skill_content_cache.sql`** (new, not yet run) - `skill_content_cache` table, keyed on (role_name, skill_name), 30-day TTL.
